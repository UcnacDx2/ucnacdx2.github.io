> 本文对公司、人物和业务细节做了脱敏，只保留与工程设计有关的部分。

我之前参与过一个上门洗车项目。

项目最开始其实不复杂：一个商户、一套运营后台、一个用户端、一个师傅端。技术栈是 Vue 3 / uni-app + NestJS + Prisma + MySQL + Redis，后端和前端都需要参与，部署也一起做。

一开始要解决的是登录、下单、支付、派单、投诉、新人券、分享返券这类典型业务。真正让我开始“踩坑”的，是后续项目突然从**单商户系统**往**加盟、多租户 SaaS**演进。

表面上看，只是“支持多个加盟商和门店”。但真正做下去以后，我才意识到：这不是给几张表加一个 `tenantId` 那么简单。

## 坑一：把“多租户”理解成给表加 tenantId

最开始很容易产生一种错觉：

> 单商户系统已经能跑了，那就在订单、用户、门店这些表上加个租户字段，不就变成 SaaS 了吗？

后来发现完全不是。

因为真正的问题不是“数据属于哪个租户”，而是**业务决策到底由谁负责**。

当时的组织关系逐渐变成了：

```text
总部
  └── 加盟商
        └── 门店
              └── 师傅
```

接下来每个功能都会冒出新的问题：

- 用户下单以后，订单应该先归属城市、加盟商还是门店？
- 一个加盟商能不能跨城市经营？
- 门店的服务范围是谁配置的？
- 总部改价格以后，加盟商是否自动生效？
- 优惠券成本由总部承担还是加盟商承担？
- 师傅到底属于门店，还是可以跨门店接单？

这些都不是数据库字段的问题，而是**领域边界的问题**。

后来我越来越认同一个做法：订单创建时，应该把关键归属关系尽可能确定下来，而不是每次查询时再动态推导。

例如一笔订单至少要明确它当时归属的经营主体、门店、服务区域。否则组织关系一变化，历史订单的含义也可能跟着变化。

### 我后来得到的教训

做多租户之前，先画业务归属图，比先改表更重要。

至少要先回答：

1. 谁拥有数据；
2. 谁能修改数据；
3. 谁承担收入和成本；
4. 谁决定规则；
5. 历史数据在组织关系变化后如何解释。

如果这几个问题没确定，`tenantId` 加得再整齐也只是把复杂度藏起来。

## 坑二：需求变化时，系统没有“演进路线”

单商户阶段，很多设计其实都默认了：

```text
系统 = 商户
```

所以很多地方根本不需要考虑“归属”。

但当系统要快速改造成 SaaS 时，这些默认假设会一起暴露出来。

比如：

- 原来全局唯一的配置，现在可能需要总部级和加盟商级；
- 原来一个价格表就够，现在可能有总部指导价、区域价、门店价；
- 原来后台管理员天然拥有所有权限，现在需要区分总部、加盟商、门店；
- 原来订单收入只是一个金额，现在需要考虑分成和结算。

当时比较痛苦的一点，就是项目并不是从第一天就按照 SaaS 设计的，却需要在很短的周期里完成这种结构升级。

这让我后来更重视一个概念：**系统不一定要一开始就做成 SaaS，但最好不要把“当前只有一个租户”写死成业务事实。**

比如配置、权限、组织关系这些东西，即使第一版只服务一个商户，也可以尽量通过明确的实体关系表达，而不是散落在代码里的各种默认值。

## 坑三：订单“属于谁”比订单状态更难

刚开始做订单系统时，我更多关注的是状态：

```text
待支付 → 待派单 → 服务中 → 已完成
```

但是在加盟模式里，更难的问题其实是：

> 这张订单到底属于谁？

用户的定位只是服务发生在哪里，并不等于经营归属。

所以后来需要同时处理：

- 用户服务地址；
- 城市或经营区域；
- 加盟商；
- 门店；
- 实际执行服务的师傅。

这几层如果混在一起，后面的派单、统计、退款、投诉、分账都会出问题。

我后来比较倾向于把订单的“业务归属”当成订单的一部分，而不是只靠关联表实时计算。

因为历史订单最重要的是：**还原下单那一刻发生了什么。**

组织结构可以变化，但历史事实不应该跟着变化。

## 坑四：支付成功，不等于钱的问题解决了

单商户阶段，支付流程往往比较直观：

```text
用户支付 → 订单支付成功
```

但一旦出现加盟商、门店、平台抽成、提现以后，问题立刻复杂很多。

我当时开始接触“分账、提现”需求以后，才真正意识到：

**支付是交易问题，结算是账务问题，两者不能混成一个状态。**

例如一笔 100 元的订单，后面可能需要回答：

- 平台收入多少？
- 加盟商收入多少？
- 是否有优惠券补贴？
- 是否存在退款？
- 哪一部分已经可以提现？
- 哪一部分仍然冻结？

如果这些东西全部靠订单表上的几个金额字段实时计算，系统很快就会变得难以解释。

现在回头看，我会更早引入“账务流水 / 结算记录”这一层，把“订单发生了什么”和“资金如何变化”拆开。

换句话说：

```text
订单系统记录业务事实
账务系统记录资金事实
```

即使第一版不做复杂会计模型，这个思路也很重要。

## 坑五：后台页面看起来像 CRUD，实际上很多是工作流

项目里有很多管理后台需求，刚看到时非常像普通 CRUD：

- 加盟商入驻审核；
- 门店管理；
- 派单；
- 投诉回访；
- 服务区域；
- 报价；
- 服务项目编辑。

如果只按照“列表 + 新增 + 编辑 + 删除”去做，很容易出现一种情况：页面都有了，但实际运营不好用。

因为很多后台功能本质是**业务流程**。

以投诉为例，它不是：

```text
修改 complaint.status
```

而更像：

```text
用户投诉
→ 运营查看
→ 联系用户
→ 记录处理过程
→ 可能退款 / 补偿
→ 完成回访
→ 关闭
```

入驻审核、派单也一样。

它们需要的是状态转换、操作记录、权限和上下文，而不只是一个数据库表的编辑器。

这也是我后来形成的一个开发习惯：

> **普通配置用 CRUD，复杂业务显式写领域逻辑。**

能通过元数据生成的管理页面就生成，不要每个页面重复写；但一旦涉及状态流转、资金、权限、审核，就不要硬塞进通用 CRUD。

## 坑六：赶功能时，最容易丢的是“可验证性”

项目后期需求变化非常快。

这种情况下，一个功能“看起来能跑”并不等于它真的可靠。

尤其是：

- 下单；
- 支付；
- 派单；
- 服务区域匹配；
- 多租户数据隔离；
- 权限。

这些功能只要其中一个条件组合没覆盖，就可能产生非常隐蔽的问题。

后来项目里开始补端到端测试时，我明显感受到：相比单纯给 Service 写很多零散单元测试，**关键业务链路的 E2E 测试价值非常高**。

例如：

```text
加盟商 A 的门店
→ 用户在其服务区域下单
→ 订单正确归属 A
→ 门店只能看到自己的订单
→ 师傅接单
→ 完成服务
```

再补一个反例：

```text
加盟商 B
→ 无法看到 A 的订单
```

这种测试实际上也是对多租户模型的一种文档。

## 坑七：抽象不是越多越好，而是要抽对地方

当项目代码开始膨胀时，很容易走两个极端。

一个极端是什么都复制：每个后台模块都写一遍 Controller、Service、CRUD 页面。

另一个极端是试图做一个“万能系统”，希望所有业务都可以通过配置生成。

我两个方向都踩过一些坑。

现在我的理解是：

### 适合抽象的

- 通用列表；
- 分页；
- 基础查询；
- 简单配置；
- 字段展示；
- 普通 CRUD。

### 不适合强行抽象的

- 下单；
- 派单；
- 分账；
- 提现；
- 审核；
- 投诉处理；
- 多角色权限决策。

这些东西的复杂度来自业务规则，而不是代码重复。

如果为了减少几十行重复代码，把真实业务规则藏进一个巨大的通用框架里，后面调试反而更困难。

## 如果现在让我重新做一次

如果重新来一次，我不会一开始就把系统做得非常“企业级”，但会先做几件事。

### 1. 先确定领域关系，再写数据库表

至少先把：

```text
总部 → 加盟商 → 门店 → 师傅
```

以及用户、订单、服务区域之间的关系画清楚。

### 2. 把订单归属设计成历史事实

订单创建时保存必要的归属信息，不依赖未来的组织结构去解释过去。

### 3. 提前把支付和结算分开

哪怕第一版结算逻辑很简单，也不要把所有资金逻辑都塞进订单状态。

### 4. 权限从“角色”升级到“角色 + 数据范围”

“加盟商管理员”这个角色本身没有意义。

真正有意义的是：

```text
这个管理员能操作哪些加盟商 / 门店 / 订单
```

### 5. 为关键业务链路写 E2E

尤其是跨租户数据隔离和订单链路。

### 6. 普通 CRUD 和领域逻辑分开

让简单的东西保持简单，让复杂的东西显式复杂。

## 最后

这个项目对我最大的价值，其实不是让我多会了几个框架 API。

而是让我第一次比较完整地感受到：

> **一个业务系统真正困难的地方，往往不是把功能写出来，而是在需求不断变化以后，系统还能不能解释自己的数据和规则。**

单商户改多租户、加盟、分账、提现，看起来是不断增加功能。

但从工程角度看，它们真正要求的是重新回答几个最基础的问题：

**谁拥有这笔数据？谁能操作它？谁承担责任？钱属于谁？历史事实怎么保存？**

这些问题如果回答清楚，代码通常只是实现。

如果没回答清楚，代码写得越快，后面偿还的复杂度可能越高。
