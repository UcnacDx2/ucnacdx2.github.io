有一次我在排查 OpenList 的一个网盘驱动，现象很简单：浏览器里已经登录，复制了一大串 Cookie 到驱动配置里，结果还是报错。

这种问题很容易让人下意识认为“Cookie 复制错了”，但真正排查下来，鉴权链路通常比一串字符串复杂得多。

## Cookie 不是一个整体凭证

浏览器 Cookie 里可能同时混着：

- 登录态；
- 统计 SDK 标识；
- 跨域状态；
- 临时会话；
- 与业务接口无关的前端参数。

驱动真正需要的，往往只是其中一小部分。复制得越多，不代表越可靠。

## 浏览器能用，不代表驱动能复现

浏览器页面可能在加载时继续执行 JavaScript，刷新 token，或者通过 SSO 再换取一次业务凭证。驱动如果只拿到静态 Cookie，却没有完成后面的兑换流程，就会出现“看起来已登录，API 仍然拒绝”的情况。

## 排障时先分层

我后来更喜欢按下面的顺序排：

1. 请求有没有发到正确接口；
2. 服务端返回的是参数错误、权限错误还是会话错误；
3. 当前凭证是否真的被接口接受；
4. 是否缺少二次 token / header；
5. 接口本身是否已经变更。

这种分层方式比不断换 Cookie 更有效。

## 最重要的是找到最小有效凭证

如果最终能确定只需要哪几个字段，就应该把驱动配置收敛到最小集合。这样既方便调试，也减少因为无关 Cookie 过期导致的随机问题。

这次排障让我再次确认：**Web 登录态和 API 鉴权是两件相关但不等价的事。**
